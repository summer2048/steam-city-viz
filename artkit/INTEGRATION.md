# 手绘素材接入记录

这份文档记录 ChatGPT 画好的 64 张图是怎么接进地图的，以及过程中做的取舍。提示词和生成流程见 [`PROMPTS.md`](PROMPTS.md)。

## 现状（2026-11-13）

- 64 个组件全部接入：36 个地标和船、27 个普通建筑、1 张树。
- 地图改为每次转 90°，共四个朝向，初始朝向转了 45°，整张图呈菱形。
- 代码绘制的版本保留为后备：某个组件没有手绘图、或图加载失败时自动使用。

## 流程

```
output/batch-0X/<组件名>.png      ChatGPT 的原图，一张图四个朝向
        │  python scripts/artkit_sprites.py
        ▼
site/sprites/<组件名>.webp        清理后的整张图
site/sprites/sprites.json         每个组件对应哪个模型、比例、四个朝向的裁切框和落地点
        │  site/js/sprites.js（浏览器里加载）
        ▼
site/js/districts.js              画地图时优先用手绘图
```

脚本读取三样东西：`site/artkit-manifest.json`（组件清单）、`artkit/refs.json`（灰模参考图的比例和落地点）、`artkit/batch-0X/ref-*.png`（灰模参考图本身）。

重画某一张图后，把新图覆盖到 `output/` 里的同名文件，重新运行脚本即可。64 张图大约需要三分钟，输出共 8.5 MB。

## 做了哪些处理

**清理**。原图已经是透明背景。脚本去掉抠图留下的几乎看不见的残影（不透明度低于 10% 的像素）；其中 6 张图是从洋红底色抠出来的，另外去掉边缘残留的洋红色。

**对齐落地点**。每栋建筑在地图上靠一个“落地点”定位。灰模参考图里这个点的位置是已知的，但 ChatGPT 画的图和灰模不会逐像素重合（实测大多数偏差在几个像素内，住宅、店面、摩天轮偏高 15% 到 40%）。所以落地点跟着画面走：保持它到建筑中线和底边的距离与灰模一致。这样画得偏高的建筑是向上长，不会陷进地面。

**比例**。沿用灰模参考图的比例，不按画面大小重新缩放。

**普通建筑的映射**。地图上的普通建筑有任意层数，手绘图只有固定的 27 种。规则是：

- 同一类建筑里选层数最接近的那张图；层数相同的几种设计（例如 `house-a` / `house-b`）轮流使用。
- 整体缩放 `(实际层数 ÷ 图的层数)^0.6`，限制在 0.84 到 1.17 倍之间，让评论更多的游戏仍然看起来更高。

**窗户亮度**。图例里“亮灯的窗”代表有 10 条以上评论的游戏占比，原来有暗、半亮、全亮三档。手绘图的灯光是画死的，所以在浏览器里把暖黄色的窗光按比例压暗，生成暗和半亮两个版本，全亮用原图。地标不做这个处理。

**树**。四棵树各是一种，随机使用；整体缩小到 0.8 倍，否则比旁边的小屋还高。

## 取舍

- **菱形地图**。手绘图是“一个角朝向观众”的视角，对应模型转 45°、135°、225°、315°。要让建筑的墙面和道路方向一致，地图本身就得停在这四个角度上，所以初始画面从正北朝上变成了转 45° 的菱形。
- **转动时的切换**。两个朝向之间没有中间帧，转到一半时建筑会直接换成下一个朝向的图。
- **高度被量化**。普通建筑的高度不再随层数连续变化，只在几种图之间跳变再加小幅缩放。高度的排序关系保留，精确比例没有保留。
- **没有重新打包**。每个组件保留原来的整张图（四个朝向在一张里），没有拼成大图集。64 个请求在本地和普通静态托管上都没有问题。

- `http://localhost:8765/models.html`：上半部分是全部手绘图，下半部分是代码绘制的模型。

## 已知问题

- 原图（56 MB）不进仓库：`output/` 已写进 `.gitignore`，打包成 `artkit-output.zip` 放在 GitHub Releases 的 `artkit-raw-v1` 下。重画了原图之后，需要重新打包并发一个新的 Release。
- 个别地标的四个朝向之间细节不完全一致（ChatGPT 生成的限制），没有逐张修正。
- 第一部分时间线的楼群不使用这套素材，仍是代码绘制。
